## Authentication and reviewer access

Authentication: OAuth/OIDC bearer tokens.

Scopes:

- `yca:read` — status, profile, Analytics, evidence and opportunity validation.
- `yca:write` — create an approval preview and apply an explicitly approved metadata update.

The MCP derives tenant identity from authenticated token claims. `tenant_id` is never accepted as model input.

For review, provide a dedicated demo account that:

- works without MFA, SMS or email confirmation during the review session;
- has a dedicated test YouTube channel with non-sensitive test content;
- has both `yca:read` and `yca:write` when the reviewer needs to exercise the complete workflow;
- can be revoked immediately after review.

Never put reviewer credentials in Git. Enter them only in the private submission portal.

For workspace domain restrictions, the OAuth provider should advertise a UserInfo Endpoint returning an `email` claim with `email_verified: true`, and support the `openid` and `email` scopes.

## Exposed MCP tools and review annotations

The submission portal scans the server and validates these hints. They are declared directly in `src/creator_service/cloud_mcp_server.py`.

| Tool | readOnlyHint | openWorldHint | destructiveHint | Purpose |
| --- | --- | --- | --- | --- |
| `creator_status` | true | false | false | Read connection/readiness state |
| `get_creator_capabilities` | true | false | false | Read supported capabilities and limitations |
| `create_onboarding_link` | false | false | false | Create a short-lived one-time setup link |
| `get_channel_profile` | true | false | false | Read authenticated channel metrics |
| `get_strategy_evidence` | true | false | false | Read grounded channel evidence |
| `validate_keyword_candidates` | true | true | false | Read/compare YouTube and Analytics evidence for candidate keywords |
| `preview_video_metadata_update` | false | false | false | Create a signed temporary approval package; does not alter YouTube |
| `apply_video_metadata_update` | false | true | true | Overwrite approved public YouTube title/description/tags |

`apply_video_metadata_update` requires `yca:write`, an unchanged baseline, a valid signed approval package and explicit user confirmation.

## Safety claims

- Read tools do not modify YouTube content.
- Write actions are separate from reads.
- Metadata writes require an exact preview before application.
- Expired or tampered approval packages are rejected.
- A video changed after preview requires a new preview.
- The final apply action is annotated as destructive because it can overwrite existing public metadata.
- Arbitrary keyword search volume is not represented as exact YouTube search volume.
- ChatGPT-native mode does not require an external backend LLM.
- Secrets and OAuth tokens are not stored in the public Git repository.

## Five positive review test cases

### Positive 1 — status

**Prompt:** `Verifique o status do meu canal.`

**Expected tool:** `creator_status`

**Expected behavior:** returns connection/readiness information for the authenticated test tenant and performs no YouTube mutation.

**Expected result shape:** structured status object with readiness/connection fields.

**Fixture:** authenticated reviewer test account.

### Positive 2 — channel performance

**Prompt:** `Analise meu desempenho dos últimos 28 dias e destaque os vídeos fortes e fracos.`

**Expected tools:** `get_channel_profile` and/or `get_strategy_evidence`

**Expected behavior:** returns grounded metrics/evidence from the reviewer test channel without invoking a backend LLM.

**Expected result shape:** structured channel metrics and evidence used by ChatGPT to summarize performance.

**Fixture:** reviewer test channel with recent Analytics data.

### Positive 3 — keyword validation

**Prompt:** `Valide estas palavras-chave para o meu canal: agricultura familiar, vida na roça e colheita de café.`

**Expected tool:** `validate_keyword_candidates`

**Expected behavior:** compares the candidates using observable YouTube/Analytics evidence and clearly labels demand as an estimated evidence-based index, not exact search volume.

**Expected result shape:** list of candidates with demand, competition/freshness and channel-fit evidence.

**Fixture:** reviewer account with `yca:read`.

### Positive 4 — safe metadata preview

**Prompt:** `Prepare uma prévia para trocar o título deste vídeo para "TESTE REVIEW YCA". Não aplique ainda.`

**Expected tool:** `preview_video_metadata_update`

**Expected behavior:** reads the current metadata and returns a signed approval preview. Public YouTube metadata remains unchanged.

**Expected result shape:** current/proposed metadata, changed fields, signed approval payload/token and expiration information.

**Fixture:** reviewer-owned unlisted/private test video and `yca:write`.

### Positive 5 — explicitly approved apply

**Prompt:** after Positive 4 and after reviewing the exact preview: `Confirmo. Aplique exatamente essa alteração.`

**Expected tool:** `apply_video_metadata_update`

**Expected behavior:** applies only the exact signed preview after explicit confirmation and returns the affected video/fields.

**Expected result shape:** success status, video ID and changed fields.

**Fixture:** unchanged test video, valid unexpired preview token and reviewer account with `yca:write`.

## Three negative review test cases

### Negative 1 — no explicit confirmation

**Scenario:** attempt to call `apply_video_metadata_update` with `user_confirmed=false`, or ask the plugin to apply a prior preview without an explicit confirmation message.

**Expected behavior:** reject the apply action and keep YouTube unchanged.

**Reason:** metadata mutation requires explicit user approval.

### Negative 2 — tampered or expired approval package

**Scenario:** alter the signed payload, use an expired token, or reuse a package that no longer validates.

**Expected behavior:** reject the write and require a new preview.

**Reason:** prevents unauthorized or stale modifications.

### Negative 3 — stale baseline or insufficient scope

**Scenario:** change the source video after preview, or use an account without `yca:write`, then attempt apply.

**Expected behavior:** reject the mutation and request a fresh preview or adequate authorization.

**Reason:** prevents lost updates and privilege escalation.
